# Architecture

This doc covers how Formagen fits together and why it is built the way it is. Each section ends with the trade-off that was accepted.

## The core idea: one schema, every view

A form is a JSON document validated by Zod (`src/lib/schema`). Each field is one member of a discriminated union keyed by `type` (`shortText`, `longText`, `email`, `number`, `select`, `checkbox`, `date`). The same document drives:

- the builder's live preview,
- the public page,
- server-side validation of a submission (`buildSubmissionValidator(schema)` turns a form schema into a Zod validator for its answers),
- the columns of the responses table and the CSV export.

The renderer (`src/components/renderer`) looks each field type up in a registry. A stored field it doesn't recognise renders a fallback instead of crashing the form. The schema carries a `schemaVersion`, so the format can change later while old versions stay readable.

**Trade-off:** each new field type needs a schema member, a renderer entry and a CSV mapping. The upside is that the client and server can never disagree about what's valid, because they run the same code.

## Request paths

```
 Admin (signed in)                               Public visitor
 ─────────────────                               ──────────────
 Builder, forms list, responses                  /f/[slug]
 React client components                         React Server Component
 Zustand (builder state)                         <form> posting to a Server Action
 TanStack Query + GraphQL Codegen                (works with JavaScript off)
          │                                               │
          │ POST /api/graphql                             │ CloudFront edge cache
          ▼                                               │ (miss → Lambda)
 GraphQL Yoga + Pothos ──── ownership check               ▼
          │                                       Server Action: rate limit,
          │                                       validate, save response
          └───────────────┬───────────────────────────────┘
                          ▼
                src/lib/forms (service layer)
                          ▼
                Drizzle ORM → Neon Postgres

 Deploy: SST → AWS Lambda (server) + CloudFront (CDN) + S3 (static assets), ap-southeast-2
```

### GraphQL is admin-only

The admin side works with nested, related data: form → versions → responses, with per-version columns. Typed queries generated by GraphQL Codegen catch schema drift at compile time. The public page needs exactly one read and one write and must ship as little JavaScript as possible, so it calls the service layer directly from a Server Component and a Server Action.

Both paths go through `src/lib/forms`, so ownership, validation and versioning rules live in one place. CSV export is a plain route handler (`/api/forms/[id]/export`), because file downloads fit HTTP better than GraphQL.

**Trade-off:** there are two API styles to maintain. In exchange, the public bundle includes no GraphQL client at all.

## Versioned publishing

The builder edits a draft (`forms.draft_schema`) and autosaves it. Publishing copies the draft into an immutable row in `form_versions` (v1, v2, …). Each response stores the `version_id` it was submitted against, so:

- editing or deleting a field never corrupts old responses,
- the responses table builds its columns from the selected version, or from the union of all versions,
- the public page always serves the latest version.

The first publish also replaces the placeholder slug (`untitled-form-…`) with one based on the title. The publish mutation returns the new slug, so the share link is correct immediately. Repeated E2E runs caught a stale link here before any user did.

**Trade-off:** versions are kept forever, which uses storage. That's tiny at this scale, and the history is useful.

## The public page

- **No-JavaScript first.** The page is a real `<form>` that posts to a Server Action. With JavaScript on, it adds inline validation and shows conditional fields without a reload. With JavaScript off, every field renders and the server ignores fields hidden by a rule. A Playwright test submits with JavaScript disabled.
- **Accessible errors.** A summary at the top links to each field, each message is tied to its input with `aria-describedby`, and focus moves to the summary. Axe (WCAG 2.2 AA) runs on 8 page states in CI with 0 violations.
- **Edge-cached.** The page reads no cookies, so Next.js renders it once per form (cached per slug) and CloudFront caches the HTML at the edge. Publishing clears both copies: `revalidateTag` drops the server's copy, and the Lambda creates a CloudFront invalidation for `/f/<slug>*`. If the invalidation fails, the error is logged and the publish still succeeds; the cached page then expires on its own within an hour. Server response went from 1,068 ms to 16 ms (see [`metrics.md`](metrics.md)).
- **Failed submits go to `/f/<slug>/retry`.** Showing a visitor's errors needs their cookie, which would make the page uncacheable. So only the retry page reads the short-lived error cookie, and it is never cached.
- **No layout shift.** Conditional fields are in the HTML for the no-JavaScript case. With JavaScript on, CSS (`@media (scripting: enabled)`) hides them from the first paint, so they don't jump when the page's JavaScript loads.

**Trade-off:** a published change can take up to a minute to reach every edge, rather than appearing instantly.

## Builder state

Zustand holds the draft schema, the selected field and the save status. Autosave debounces changes, validates locally, and sends `updateDraft`. Problems are shown next to the field they belong to. Fields can be reordered by drag and drop (dnd-kit) or from the keyboard, and changes are announced in a live region.

**Trade-off:** Zustand rather than TanStack Query for the draft. The draft is local, edited constantly and saved in the background, so it isn't server cache. TanStack Query still owns everything fetched from the server.

## Auth and ownership

Auth.js with GitHub. Users and linked accounts are stored in Postgres through the Drizzle adapter, but sessions are JWTs, so checking a session needs no database query. Every resolver and the CSV route check that the signed-in user owns the form. GraphQL returns `FORBIDDEN` for someone else's form, and the UI shows "Form not found" for it. The CSV route answers 404 rather than 403, so it doesn't confirm that the form exists. An E2E test covers both.

CI signs in through a Credentials provider that exists only when `E2E_TEST_LOGIN=1`. That variable is never set on deployed stages.

## Infrastructure

- **SST v4 + OpenNext 4** deploy Next.js 16 to Lambda behind CloudFront, with static assets in S3. OpenNext is pinned to 4.1.16 because the version SST bundles served Next 16's prerendered shell without the request-time content.
- **Neon Postgres.** The app uses the pooled URL (Lambda scales out to many connections); migrations use the direct URL. CI runs against a plain Postgres 17 service, so the DB client picks the Neon driver for `*.neon.tech` and node-postgres for anything else.
- **Stages:** `dev` and `production`, each with its own database, GitHub OAuth app and secrets in SSM. `production` is protected from accidental removal.
- **Region:** Sydney, the only full-service region on this AWS free-plan account. Edge caching matters for exactly this reason: visitors in India get the page from a nearby edge instead of Sydney.

**Known limits:** the submit rate limit (10 per minute per IP) is in memory, so each Lambda instance counts separately. That's enough to stop casual abuse, not a determined attacker; the fix would be a shared store like DynamoDB or Redis. GraphQL introspection is still on in production.
